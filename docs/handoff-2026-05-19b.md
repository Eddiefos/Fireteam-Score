# Fireteam Score — Handoff #2 (2026-05-19)

Read the first handoff doc (`docs/handoff-2026-05-19.md`) before this one. That covers the Supabase + auth foundation. This document covers the **multi-player rounds** feature that was added on top of it.

---

## What changed

The app was single-player. Rounds had one player (the logged-in user), scores were keyed by `user_id`. That is now gone. Rounds support any mix of registered users and named guests, tracked through a new `round_players` table that acts as the canonical player identity within a round.

### New tables (need the migration applied — see below)

**`friends`** — mutual friend system. Each row is a friend relationship between two users.
```
id, requester_id, addressee_id, status ('pending'|'accepted'|'declined'), created_at
unique (requester_id, addressee_id)
```

**`round_players`** — one row per player per round. Supports both registered users and guests.
```
id, round_id, user_id (nullable), guest_name (nullable), display_name, initials, color, is_guest
check: user_id is not null OR guest_name is not null
```

**`scores` (altered)** — `round_player_id` column added; `user_id` made nullable. Unique constraint changed from `(round_id, user_id, hole_number)` to `(round_id, round_player_id, hole_number)`.

Full migration SQL: `supabase/migrations/20260519000000_multiplayer_rounds.sql`

> **This migration has NOT been applied to Supabase yet.** Run it in the SQL editor before testing the app end-to-end.

## Round assembly pattern (updated)

The score map is now keyed by `round_player_id` (not `user_id`). Screens build the in-memory round object like this:

```js
// In LiveScorecardScreen and RoundDetailScreen
const { players, loading: playersLoading } = useRoundPlayers(activeRound?.id)
const { scores } = useScores(activeRound?.id)

const round = useMemo(() => {
  if (!activeRound || !course) return null
  const pars = course.pars
  const scoreMap = {}
  for (const p of players) scoreMap[p.id] = Array(pars.length).fill(null)
  for (const s of scores) {
    if (scoreMap[s.round_player_id]) scoreMap[s.round_player_id][s.hole_number - 1] = s.strokes
  }
  return { ...activeRound, pars, players, scores: scoreMap, createdBy: activeRound.created_by }
}, [activeRound, course, players, scores])
```

Key invariant: `round_players.id` is the score key everywhere — in state, in DB, in the Realtime payload.

## Score submission

```ts
submitScore(roundPlayerId: string, userId: string | null, holeNumber: number, strokes: number)
```

- `holeNumber` is 1-indexed
- `roundPlayerId` is `round_players.id` (not `user_id`)
- Optimistic update fires immediately; DB write follows
- If offline: queued to IndexedDB, flushed on `window.online`
- Realtime subscription receives server-confirmed scores and upserts them by `(round_player_id, hole_number)`

The round creator can score on behalf of guests (and registered players who haven't scored yet). This is enforced in the RLS policy: `auth.uid() = user_id OR auth.uid() = rounds.created_by`.

## StartRoundScreen changes

The player picker now:
1. Pre-adds the logged-in user as an immovable first chip
2. Lists friends from `useFriends` with a toggle button (+/✓)
3. Has an inline guest input (type name → Add → appears as chip)
4. Assigns colours sequentially from `PLAYER_COLORS` array
5. On "Start Round" calls `startRound(courseId, allPlayers)` where `allPlayers` is `NewRoundPlayer[]`

## LiveScorecardScreen changes

- Uses `useRoundPlayers` instead of `useProfile` for the players array
- `myPlayer = players.find(p => p.userId === currentUserId) ?? players[0]`
- `isCreator = round.createdBy === currentUserId`

- **Inline override picker**: if you're the creator, you can tap any other player's card to score on their behalf (sets `inlinePicker` state to their `roundPlayerId`)
