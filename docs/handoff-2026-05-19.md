# Fireteam Score — Handoff Document (2026-05-19)

This doc brings you up to speed on **Fireteam Score**, a disc golf scorekeeper PWA. Read CLAUDE.md in the repo root for the full project spec and design system. This document covers what has been built, key decisions made, and what's next.

---

## What is this app?

A Progressive Web App for scoring disc golf rounds with your "fireteam" (squad). Five screens: Home, Start Round, Live Scorecard, End of Round (Round Detail), Stats/History. Built in React 18 + Vite. Backend is Supabase (Auth + Postgres + RLS). Deployed as a PWA with offline support.

## Key architecture decisions

### Service layer
All Supabase calls are in `src/services/`. Components never call `supabase.from()` directly. Always go through service functions or the hooks that wrap them.

### Hook contracts

```ts
useAuth()        → { user, loading }
useProfile(uid)  → { profile, loading, updateProfile }
useCourses(uid)  → { courses, loading, createCourse, updateCourse, deleteCourse }
useRounds(uid)   → { rounds, activeRound, loading, startRound, finishRound, abandonRound, refresh }
useScores(rid)   → { scores, loading, submitScore }
```

**Important:** `useRounds` returns sparse round rows — no `players`, `scores`, or `pars`. Screens build a full in-memory round object by joining with `useCourses` (for pars) and `useScores` (for score data). Both `LiveScorecardScreen` and `RoundDetailScreen` contain this assembly logic:

```js
// Canonical round assembly pattern (used in LiveScorecardScreen + RoundDetailScreen)
const course = courses.find(c => c.id === activeRound.course_id)
const pars = course?.pars ?? []
const players = [{ id: userId, name: profile.display_name, color: profile.avatar_color }]
const scoreMap = {}
for (const p of players) scoreMap[p.id] = Array(pars.length).fill(null)
for (const s of scores) {
  if (scoreMap[s.user_id]) scoreMap[s.user_id][s.hole_number - 1] = s.strokes
}
const round = { id, courseName, startedAt, completedAt, pars, players, scores: scoreMap, status }
```

### Score submission
`submitScore(roundId, userId, holeNumber, strokes)` — `holeNumber` is **1-indexed**. Uses Supabase upsert (`onConflict: 'round_id,user_id,hole_number'`). If offline, queues to IndexedDB and flushes when `window.online` fires.

### Single-player scope
Rounds are single-player right now. `players` array always has one entry (the logged-in user). Multi-player scoring and the fireteam social layer are the **next spec** (see below).

### App router
`App.jsx` is purely a router (~197 lines). It holds `screen`, `params`, `authView` state, calls `useAuth()` + `useProfile()`, and renders the appropriate screen component. Screen components receive `go`, `userId` (and `onToast` for CoursesScreen). Screens never receive data as props — they call their own hooks.

### Offline score undo
The `LiveScorecardScreen` uses a local `localClears` Set to handle score clearing/undo UI. Clearing a score locally shows "—" in the UI and lets the player re-tap. If they navigate away without re-entering, the old score remains in Supabase (which is correct — the score stood).

### Auth
Supabase magic link (email). Profile row is auto-created by a Postgres trigger on `auth.users` insert. `useAuth` wraps `onAuthStateChange`. The `session` object from the old localStorage era is gone — components use `user` from `useAuth()`.

## Design system

All colours via the `FT` token object imported from `src/constants/colors.ts`. Never use raw hex strings in components. Font stacks are `SF`, `SFR` (rounded), `MONO` from the same file.

Key colours:
- `FT.forest` `#1F3D2B` — primary dark green, headers, selected states
- `FT.cream` `#F4EFE4` — main background
- `FT.orange` `#FF6B1F` — CTA, birdies, accents
- `FT.ink` `#15110D` — body text

## What's next: Fireteams

The next spec to implement is **Fireteams** — the social layer that makes multi-player scoring possible. This work is not started yet. Key things it needs to deliver:

1. **Fireteam creation** — a user creates a fireteam, gets an invite code
2. **Join by invite code** — friend enters code, becomes a `fireteam_member`
3. **Member roster** — display fireteam members with avatars/colours
4. **Multi-player round start** — select which fireteam members are playing
5. **Multi-player live scoring** — `players` array has all participants, scores tracked per player
6. **Round detail with all players** — leaderboard, scorecard with multiple rows
7. **Stats that work** — `computePlayerStats` needs real multi-player round data to produce non-zero stats

The `fireteams` and `fireteam_members` tables already exist in the DB schema (see CLAUDE.md §4.2). The `SquadScreen` placeholder exists in `src/screens/AuthScreens.jsx` (currently empty shell).

The design spec for Fireteams has not been written yet. Start with `/brainstorm` or write the spec directly following the pattern in `docs/superpowers/specs/`.
